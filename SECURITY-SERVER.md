# Базовая безопасность сервера — план

Заказ владельца 20.09.2026. **Сейчас не выполняем** — сначала тесты. Здесь
записан порядок, чтобы не потерять и чтобы не отрезать себе доступ.

Относится к тестовому серверу `193.233.223.130` и, что важнее, к будущему
боевому серверу в РФ.

---

## Золотое правило всей этой работы

**Никогда не закрывать старую дверь, пока не проверил новую — в ДРУГОМ окне
терминала.** Первое окно остаётся открытым как страховка: если новый вход не
заработает, через него всё можно вернуть. Закрыли оба окна раньше времени —
остаётся только переустановка сервера, то есть всё с нуля.

Маленькое уточнение к формулировке заказа: **приватный ключ остаётся на Маке**
(`~/.ssh/condur_server`), а на сервер уезжает **публичный**
(`~/.ssh/condur_server.pub`). Публичный — это замок, он и должен лежать
открыто; приватный — сам ключ, он не покидает компьютер.

## Порядок работ

### 1. Обновить пакеты

```bash
apt-get update && apt-get -y full-upgrade && apt-get -y autoremove
```

Перезагрузка, если обновилось ядро (`/var/run/reboot-required`). Наши службы
поднимутся сами — проверено 20.09: `docker` в автозапуске, у контейнеров
`restart: unless-stopped`.

### 2. Включить автоматические обновления безопасности

```bash
apt-get install -y unattended-upgrades && dpkg-reconfigure -plow unattended-upgrades
```

Чтобы дыры закрывались без нас. Обновляются только security-пакеты.

### 3. Создать отдельного пользователя с sudo

```bash
adduser --gecos "" condur
usermod -aG sudo condur
mkdir -p /home/condur/.ssh && cp /root/.ssh/authorized_keys /home/condur/.ssh/
chown -R condur:condur /home/condur/.ssh && chmod 700 /home/condur/.ssh && chmod 600 /home/condur/.ssh/authorized_keys
```

Зачем: чтобы в обычной работе не быть «хозяином всего». Ошибка от обычного
пользователя портит меньше, чем ошибка от root.

### 4. ПРОВЕРИТЬ новый вход во втором окне терминала

Старое окно с root **не закрывать**. В новом:

```bash
ssh -i ~/.ssh/condur_server condur@193.233.223.130 'whoami && sudo -n true && echo "sudo работает"'
```

Ждём `condur` и `sudo работает`. Не вышло — чиним из первого окна.
(`sudo -n` — без запроса пароля; если пароль спросит, значит нужен
`NOPASSWD` в `/etc/sudoers.d/condur` или пароль придётся вводить руками.)

### 5. Только теперь запретить вход по паролю

```bash
sed -i 's/^#\?PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#\?PermitRootLogin .*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
sshd -t && systemctl reload ssh
```

`sshd -t` проверяет файл до перезапуска: с ошибкой в конфиге служба не
поднимется и доступ пропадёт.

`prohibit-password` для root, а не `no`: root по ключу остаётся — им ходят
наши скрипты выкладки. Полностью закрыть root можно после пункта 6.

⚠️ **На Aeza вход по паролю нужен для их веб-консоли.** Отключив пароль в
ssh, консоль в панели продолжит работать — это отдельный канал. Но если
потеряется и ключ, и пароль root, останется только переустановка.

### 6. Если решим закрыть root совсем

Тогда придётся переписать `~/Downloads/condur-ru-test/выложить-на-сервер.sh`:
сейчас он ходит `root@IP`. Нужно будет `condur@IP` + `sudo` внутри команд.
Работы на полчаса. **Пока root по ключу оставляем** — иначе выкладка сломается.

### 7. Брандмауэр

```bash
ufw default deny incoming && ufw default allow outgoing
ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw allow 9000/tcp
ufw --force enable
```

Порт 9000 — приём GPS, без него трекеры не достучатся.
⚠️ Docker умеет обходить ufw (пишет свои правила в iptables) — после
включения проверить снаружи, что закрытые порты действительно закрыты.

### 8. Защита от перебора

```bash
apt-get install -y fail2ban && systemctl enable --now fail2ban
```

На Ubuntu 26.04 частично это уже делает сам OpenSSH (`PerSourcePenalties` —
из-за него 20.09 рвалась выкладка).

## Что относится к самой программе, а не к серверу

Найдено при тестах 20.09.2026:

1. **Приём GPS пускает кого угодно.** Проверено с Мака: Wialon-вход
   `#L#863151076883336;NA` и с выдуманным паролем `12345` — оба отвечают
   `#AL#1` (принято). Причина: `TELEMETRY_PASSWORD` не задан ни здесь, ни на
   Railway. Кто знает адрес, порт и номер объекта — может слать фальшивые
   координаты. **Задать `TELEMETRY_PASSWORD`** (и у Ставтрэка в настройках
   ретрансляции — тот же пароль).
2. **Нет предела числу соединений:** `EGTS_MAX_CONNECTIONS=0`. Поставить
   50–200, иначе один поток мусора съест память.
3. **Postgres и Redis на Railway** — выключить публичный доступ (PROBLEMS №37).
4. **Репозиторий `gipew09-cloud/condur` публичный** — закрыть.
5. **Бэкап базы ни разу не восстанавливали** (PROBLEMS №11). Проверить
   восстановление на тестовом сервере — он для этого и есть.
6. **Мусор на порт 9000 отбивается правильно:** «просто текст» и нулевые
   байты — соединение закрывается сразу, не висит.

---

## Чего НЕ делать

- Не отключать root, пока не переписан скрипт выкладки.
- Не включать ufw «вслепую», не открыв 9000 — трекеры замолчат, и это не
  будет видно сразу.
- Не менять `sshd_config` без `sshd -t`.
- Не делать всё это на боевом сервере в рабочее время.
